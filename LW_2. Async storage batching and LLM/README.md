# Agro Scoring API

REST API на FastAPI для оценки риска сельскохозяйственных предприятий. Сервис принимает данные одного хозяйства или пакета в формате JSON, рассчитывает оценку риска, определяет категорию и рекомендацию, сохраняет результаты и позволяет получить их по идентификатору или в списке прогнозов.

Готовый результат возвращается в рамках одного HTTP-запроса после сохранения в SQLite. Обращения к базе выполняются асинхронно через `aiosqlite`. Документация OpenAPI и интерфейс Swagger UI формируются автоматически.

Маршрут `/llm/chat` передаёт текстовый запрос внешней LLM. `/predict-with-llm` дополняет сохранённый результат скоринга текстовым объяснением. Ответы LLM сопровождаются метаданными и временем внешнего вызова.

## Запуск на Windows

Проект проверен с Python 3.14.3. Версии зависимостей зафиксированы в `requirements.txt`.

Скачайте или склонируйте репозиторий. Откройте PowerShell в корне проекта, где находятся `main.py` и `requirements.txt`, и выполните:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

Команды установки зависимостей и запуска используют Python созданного виртуального окружения. Параметр `--reload` включает автоматический перезапуск при изменении исходного кода и предназначен для локальной разработки. Для остановки сервера нажмите `Ctrl+C`.

После запуска доступны:

- [Swagger UI](http://127.0.0.1:8000/docs) — описание API и выполнение запросов.
- [OpenAPI JSON](http://127.0.0.1:8000/openapi.json) — спецификация API.
- [Health](http://127.0.0.1:8000/health) — проверка доступности сервиса.

## API

| Метод | Маршрут | Назначение | Успешный ответ |
|---|---|---|---|
| GET | `/health` | Проверка доступности API | 200, `{"status": "ok"}` |
| GET | `/model-info` | Название, версия, тип и готовность модели | 200, JSON с метаданными |
| GET | `/queue-status` | Размер очереди и параметры пакетной обработки | 200, JSON с состоянием |
| POST | `/predict` | Расчёт риска и сохранение результата | 200, JSON с прогнозом |
| POST | `/batch-predict` | Один пакетный расчёт для 1–8 хозяйств и сохранение одной транзакцией | 200, общий ID и список результатов |
| POST | `/predict-queued` | Расчёт одного хозяйства через очередь и динамический пакет | 200, JSON с прогнозом |
| POST | `/llm/chat` | Текстовый запрос к внешней LLM | 200, ответ модели и метаданные |
| POST | `/predict-with-llm` | Расчёт и сохранение риска с последующим объяснением LLM | 200, объекты `prediction` и `llm` |
| GET | `/predictions/by-weekday` | Страница прогнозов за выбранный день недели | 200, объект с `data` и `meta` |
| GET | `/predictions/{request_id}` | Получение сохранённого прогноза по ID | 200, JSON с прогнозом |
| GET | `/requests/{request_id}/predictions` | Все прогнозы одного HTTP-запроса | 200, массив прогнозов |
| GET | `/predictions` | Получение последних прогнозов | 200, массив прогнозов |

`GET /predictions` принимает два query-параметра:

- `limit` — количество результатов: от 1 до 100, по умолчанию 10.
- `risk_level` — категория `low`, `medium` или `high`; параметр необязательный.

Прогнозы возвращаются от новых к старым. Фильтрация по категории выполняется до ограничения количества результатов.

Пример: `GET /predictions?limit=2&risk_level=high` возвращает до двух последних прогнозов с высоким риском.

`GET /requests/{request_id}/predictions` возвращает массив всех прогнозов с указанным ID, включая случай с одним элементом. Если записей нет, возвращается 404. Для получения одного объекта используйте `/predictions/{request_id}`; при нескольких совпадениях этот маршрут возвращает 409 и указывает маршрут списка.

`GET /predictions/by-weekday` принимает параметры:

- `weekday` — обязательный день недели: `monday`, `tuesday`, `wednesday`, `thursday`, `friday`, `saturday`, `sunday`. Регистр букв не учитывается.
- `page` — номер страницы от 1, по умолчанию 1.
- `per_page` — число записей на странице от 1 до 100, по умолчанию 5.

Пример: `GET /predictions/by-weekday?weekday=wednesday&page=1&per_page=5`.

День недели определяется по `created_at` в UTC. Записи сортируются по убыванию `id`, затем выбираются через SQL `LIMIT` и `OFFSET`. Ответ содержит `data` со списком прогнозов и `meta`: `weekday`, `current_page`, `per_page`, `total_pages`, `total_items`, `next_page`, `prev_page`. Ссылки соседних страниц сохраняют день недели и размер страницы; если перехода нет, ссылка равна `null`. Число строк и содержимое страницы читаются в одной транзакции.

Для дня без записей первая страница возвращает 200 с пустым `data` и нулевыми счётчиками. Запрос несуществующей страницы возвращает 404.

### Ошибки

- **400** — неизвестный регион, категория риска или день недели.
- **404** — прогноз с указанным `request_id` не найден либо запрошенная страница не существует.
- **409** — с указанным `request_id` связано несколько прогнозов, поэтому одиночный результат неоднозначен.
- **422** — запрос не соответствует схеме или ограничениям параметров.
- **429** — очередь заполнена; ответ содержит `Retry-After: 1`.
- **502** — внешний LLM API вернул ошибку, некорректный JSON, ответ неподходящей структуры или объяснение, не согласованное с прогнозом.
- **503** — модель или worker недоступны, произошёл сбой хранилища либо ошибка соединения с LLM.
- **504** — превышено время ожидания: 2 секунды для скоринга (включая очередь и блокировку модели) или 60 секунд для LLM.
- **500** — внутренняя ошибка сервиса.

Ошибки возвращаются в JSON с полями `detail` и `request_id`. Для 422 поле `detail` содержит список ошибок валидации FastAPI. Подробности внутренних ошибок записываются в журнал; при HTTP 500 клиент получает сообщение `Internal server error`, при сбое SQLite — `Prediction storage is unavailable`.

## Данные запроса

Все поля тела `POST /predict` обязательны.

| Поле | Тип | Описание и ограничения |
|---|---|---|
| `farm_id` | string | Непустой идентификатор хозяйства |
| `region` | string | Регион: `Krasnodar`, `Rostov` или `Stavropol` |
| `crop_type` | string | Непустое название основной культуры |
| `area_ha` | number | Площадь посевов в гектарах, больше 0 |
| `temperature_avg` | number | Средняя температура в °C, от −60 до 60 включительно |
| `precipitation_mm` | number | Количество осадков в миллиметрах, не меньше 0 |
| `payment_delay_days` | integer | Длительность просрочки в днях, не меньше 0 |
| `previous_defaults` | integer | Число предыдущих дефолтов, не меньше 0 |
| `debt` | number | Текущая задолженность, не меньше 0 |

Числовые поля типа `number` должны содержать конечные значения. Pydantic проверяет структуру и ограничения данных, затем сервис проверяет регион по справочнику.

## Пакетный расчёт

`POST /batch-predict` принимает объект с полем `items` — списком от 1 до 8 объектов той же структуры, что и запрос `/predict`. Пример из трёх хозяйств находится в [examples/batch.json](examples/batch.json): ожидаемые оценки 0.1 (`low`), 0.4 (`medium`) и 0.9 (`high`).

В [examples/batch_too_large.json](examples/batch_too_large.json) находится запрос из девяти объектов для проверки ограничения размера: ожидается 422 без расчёта и сохранения.

Все элементы проходят валидацию до расчёта. Модель получает весь список одним вызовом `model_predict_batch()`, после чего результаты записываются через один `executemany()` и один `commit()`. У записей отдельные первичные ключи `id`, общий `request_id` и `source = batch`. При ошибке во время записи весь пакет откатывается. Успешный ответ возвращается после фиксации транзакции.

Ответ содержит общий `request_id`, `batch_size`, `processing_time_ms` и `items`. Элементы `items` возвращаются в порядке входного списка и содержат `farm_id`, `risk_score`, `risk_level`, `recommendation`, `model_version`. Время `processing_time_ms` охватывает вызов модели, формирование результатов и сохранение в SQLite. Заголовок `X-Process-Time` измеряет обработку HTTP-запроса в секундах.

Все строки пакета можно прочитать через `/requests/{request_id}/predictions`. Одиночный маршрут `/predictions/{request_id}` возвращает 409, если пакет содержит несколько результатов.

Одиночный `/predict` использует тот же вызов модели со списком из одного хозяйства. Доступ к модели сериализуется через `asyncio.Lock`. Длительность вызова задана как 20 мс плюс 3 мс на объект; эти параметры и ограничение 8 объектов находятся в `config.py`. Таймаут ожидания модели составляет 2 секунды; при его превышении возвращается 504 без сохранения результата. Числовые правила оценки риска остаются теми же.

## Очередь и динамические пакеты

`POST /predict-queued` принимает одно хозяйство той же структуры, что и `/predict`. Запрос помещается в очередь со своим `request_id` и `Future`. Фоновый worker берёт первую задачу и накапливает пакет до 8 объектов или до истечения 50 мс. Затем выполняется один вызов модели; каждый ожидающий HTTP-запрос получает свою оценку и сохраняет отдельный прогноз с `source = queued` до ответа 200.

Запрос ожидает результат в рамках того же HTTP-соединения. В динамическом пакете у каждого запроса свой ID. Это отличается от `/batch-predict`, где клиент передаёт весь список одним запросом с общим ID.

Очередь вмещает до 100 ожидающих задач. При заполнении `/predict-queued` возвращает 429 и `Retry-After: 1`. Ожидание результата ограничено 2 секундами; превышение даёт 504 без сохранения прогноза. Истёкшие и отменённые запросы пропускаются при формировании пакета. Если Future отменён во время общего расчёта, worker пропускает передачу результата этому запросу.

Worker запускается через lifespan и останавливается вместе с приложением. При остановке незавершённые ожидающие запросы освобождаются с 503, очередь очищается. В журнале `Dynamic batch formed` фиксируются размер пакета и ID вошедших в него запросов.

### Состояние очереди

При запуске приложение создаёт `asyncio.Queue` ёмкостью 100 запросов. `GET /queue-status` возвращает текущий `queue_size`, фактическую ёмкость `queue_max_size`, `max_batch_size` (8), `max_batch_wait_ms` (50) и `inference_timeout_seconds` (2.0).

`queue_size` учитывает задачи, которые worker ещё не извлёк. Выбранные для обработки задачи уже находятся вне очереди, поэтому нулевой размер возможен и во время расчёта. Очередь хранится в памяти одного процесса приложения. `/predict` и `/batch-predict` вызывают модель напрямую и используют ту же блокировку модели.

### Проверка основных ответов API

При работающем сервере запустите из корня проекта в другом терминале с активированным окружением:

```powershell
python .\scripts\check_api_basics.py --output ..\report\api_basics_result.json
```

Скрипт проверяет `/health`, успешный `/predict`, отказ 400 для неизвестного региона, чтение сохранённого прогноза и отказ 404 для неизвестного ID. Проверяются заголовки `X-Request-ID` и `X-Process-Time`, содержимое ответов и отсутствие записи после отказа 400. Номера строк 1, 2, 4, 5, 6 соответствуют сценариям проверки сервиса. Ожидаемый итог — `Basic API checks: PASS`.

Успешный запрос добавляет один прогноз `FARM-BASELINE-HIGH` в рабочую базу. LLM не вызывается. Таблица показывает время сервера из `X-Process-Time` и время HTTP-запроса со стороны клиента; это отдельные наблюдения, а не статистическая оценка производительности. Необязательный `--output` сохраняет ответы, ID, результаты проверок и длительности в JSON. Адрес сервера можно изменить через `--url`.

### Проверка одновременных запросов

При работающем сервере запустите из корня проекта в другом терминале с активированным окружением:

```powershell
python .\scripts\check_dynamic_batch.py --output ..\report\dynamic_batch_result.json
```

Скрипт использует стандартную библиотеку Python и одновременно отправляет восемь отдельных запросов в `/predict-queued`. Данные берутся из примеров `low.json`, `medium.json` и `high.json`; для каждого запроса создаются отдельный `X-Request-ID` и идентификатор хозяйства. Проверяются HTTP 200, совпадение ID в теле и заголовке, хозяйство, оценка и категория риска. Успешные запросы сохраняют восемь прогнозов в рабочую базу.

В терминале выводятся результаты и время каждого запроса со стороны клиента. Флаг `--output` необязателен: он сохраняет JSON с результатами, настройками очереди и ID запуска по указанному пути. Адрес сервера можно изменить через `--url`.

В журнале сервера найдите строки `Dynamic batch formed | size=...` с ID текущего запуска `dyn-...`. Размер больше одного подтверждает объединение отдельных запросов в общий вызов модели. Из-за времени поступления восемь запросов могут распределиться по нескольким пакетам; успешные HTTP-ответы сами по себе не показывают размеры этих пакетов. Измеренное клиентом время включает HTTP-обмен, ожидание очереди, расчёт и сохранение результата.

### Проверка переполнения очереди

Из корня проекта с активированным окружением:

```powershell
python .\scripts\check_backpressure.py --output ..\report\backpressure_result.json
```

Скрипт самостоятельно запускает отдельный сервер на `127.0.0.1:8001` с временной SQLite-базой. В этом процессе используются очередь ёмкостью 2, пакет из одного объекта без окна накопления, фиксированная задержка модели 1 с и таймаут 5 с. Эти параметры делают переполнение наблюдаемым; файл `config.py`, основной сервер и его база остаются прежними. Если порт занят, можно указать `--port 0`, чтобы ОС выбрала свободный порт.

Отправляются восемь параллельных запросов. Проверка ожидает успешные ответы 200 и хотя бы один отказ 429; точное количество зависит от времени поступления запросов. Для 429 проверяются `Retry-After: 1` и совпадение ID в теле и заголовке. Через API истории проверяется сохранение принятых прогнозов и отсутствие отклонённых. Дополнительный запрос после разгрузки должен получить 200, очередь в конце должна быть пустой.

Результат `Backpressure checks: PASS` означает, что все эти условия выполнены. JSON-отчёт и журнал сервера с суффиксом `.server.log` сохраняются рядом. После проверки сервер останавливается, временная база удаляется. Длительности в этом режиме относятся к указанной конфигурации проверки.

### Проверка таймаута инференса

```powershell
python .\scripts\check_inference_timeout.py --output ..\report\inference_timeout_result.json
```

Скрипт запускает отдельный сервер на `127.0.0.1:8001` с временной базой. Только в этом процессе лимит ожидания устанавливается в 0.001 с; длительность вызова модели для одного объекта составляет 0.023 с, окно накопления очередного пакета — 50 мс. `/predict`, `/batch-predict` и `/predict-queued` должны вернуть HTTP 504 с `detail = Inference timeout` и совпадающим ID в теле и заголовке. В очередном режиме лимит также охватывает ожидание формирования пакета.

Затем в том же процессе лимит возвращается к 2 с и выполняется успешный запрос через тот же worker. По истории проверяются отсутствие результатов трёх запросов с таймаутом и сохранение восстановительного прогноза. Ожидаемый итог — `Inference timeout checks: PASS`. Отчёт и журнал сохраняются рядом; сервер останавливается и временная база удаляется. Файлы конфигурации и рабочая база остаются прежними. При занятом порте используйте `--port 0`.

## Пример расчёта

Пример тела запроса из `examples/high.json`:

```json
{
  "farm_id": "FARM-003",
  "region": "Krasnodar",
  "crop_type": "wheat",
  "area_ha": 2500,
  "temperature_avg": 24.3,
  "precipitation_mm": 320,
  "payment_delay_days": 45,
  "previous_defaults": 1,
  "debt": 6500000
}
```

Его можно отправить через Swagger UI или из PowerShell, находясь в корне проекта:

```powershell
$farmRequest = Get-Content -Raw -Encoding UTF8 .\examples\high.json
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/predict" -ContentType "application/json" -Body $farmRequest
```

Пример ответа; вместо `<UUID>` сервис возвращает сгенерированный идентификатор, если клиент не передал собственный `X-Request-ID`:

```json
{
  "request_id": "<UUID>",
  "farm_id": "FARM-003",
  "risk_score": 0.9,
  "risk_level": "high",
  "recommendation": "Высокий риск. Требуется ручное рассмотрение",
  "model_version": "1.0"
}
```

По `request_id` из ответа можно получить этот результат через `GET /predictions/{request_id}` либо массив результатов через `GET /requests/{request_id}/predictions`.

## Текстовый запрос к LLM

`POST /llm/chat` принимает JSON из `examples/llm_chat.json`:

```json
{
  "prompt": "Объясни в двух предложениях, зачем API нужен request_id.",
  "model": "auto",
  "temperature": 0.3,
  "max_tokens": 300
}
```

`prompt` обязателен и содержит от 1 до 5000 символов. Остальные поля необязательны: `model` по умолчанию `auto`, `temperature` — 0.3 (диапазон 0–2), `max_tokens` — 300 (диапазон 1–2000). Текст передаётся во внешний API [Vireonix](https://vireonix.ai/docs) по адресу `https://vireonix.ai/v1/chat/completions`, без API-ключа и заголовка Authorization.

Ответ содержит `request_id`, `requested_model`, `returned_model`, `answer`, `reasoning`, `finish_reason`, `usage`, `latency_ms`. Необязательные метаданные могут быть `null`. `latency_ms` измеряет внешний HTTP-вызов, а `X-Process-Time` — обработку всего входящего запроса. Самостоятельный `/llm/chat` не создаёт прогнозов в SQLite.

Один `httpx.AsyncClient` создаётся через lifespan, переиспользуется запросами и закрывается при остановке. Весь внешний вызов ограничен 60 секундами; HTTPX также ограничивает отдельные сетевые операции. Ошибка статуса провайдера и некорректный ответ дают 502, ошибка соединения — 503, таймаут — 504. Повторные запросы автоматически не отправляются. В журнале фиксируются ID, модель, задержка и причина завершения; промпт и сгенерированный текст не записываются.

Адрес, модель, таймаут и значения генерации по умолчанию находятся в `config.py`.

Для диагностики в журнале также отражаются маршрут провайдера `provider_route` и причина отклонения объяснения `reason`. При несовпадении повторённых полей дополнительно записываются ожидаемые и полученные балл и категория. Полный ответ и исходные показатели хозяйства в эти записи не включаются.

## Скоринг с объяснением LLM

`POST /predict-with-llm` принимает те же девять полей хозяйства, что и `/predict`. Готовый пример — `examples/predict_with_llm.json`.

Сначала выполняется обычный расчёт риска и сохраняется прогноз с `source = single+llm`. После успешного `commit()` формируется запрос к LLM. В него входят только `risk_score`, `risk_level`, `recommendation` и `model_version`; идентификаторы хозяйства и HTTP-запроса, исходные финансовые и прочие показатели внешнему API не передаются.

Общие инструкции объяснения передаются отдельным сообщением `system`. Сообщение `user` содержит только короткий JSON текущего результата с четырьмя указанными полями. Такое разделение убирает длинный общий текст из сообщения с данными. Инструкции требуют JSON с `risk_score`, `risk_level` и `explanation`; объяснение должно содержать 2–4 предложения, сохранять смысл рекомендации, учитывать правила банка и не придумывать причины. Ответ проверяется: повторённые поля должны точно совпасть с прогнозом; явные упоминания иных баллов или категорий в тексте отклоняются. Неверная структура или несогласованность дают 502 с `LLM explanation failed scoring consistency checks`. Клиент получает проверенный текст в обычном поле `llm.answer`, внутренний JSON не меняет публичную структуру ответа.

Внешним запросам передаётся `Cache-Control: no-cache, no-store`; этот заголовок не гарантирует отключение внутреннего кэша провайдера. Проверка согласованности действует независимо от кэширования. Она обнаруживает проверяемые несоответствия полей и явные числовые/категориальные противоречия; точность причин и соответствие рекомендации продолжают оцениваться отдельно. Числовой прогноз задаётся алгоритмом скоринга.

Успешный ответ содержит `prediction` с сохранённым прогнозом и `llm` с текстом и метаданными. В обоих объектах один `request_id`, совпадающий с заголовком. В SQLite сохраняется прогноз; текст объяснения возвращается клиенту. `X-Process-Time` включает расчёт, сохранение и внешний вызов, а `llm.latency_ms` — только внешний HTTP-вызов.

Если ошибка произошла на этапе LLM, уже сохранённый прогноз остаётся доступен через `GET /requests/{request_id}/predictions` или одиночный поиск. Используйте ID из JSON ошибки либо заголовка ответа. Ошибка валидации, расчёта или сохранения останавливает обработку до обращения к LLM. Повторный POST запускает новый расчёт; дедупликация по `X-Request-ID` не выполняется.

## Расчёт риска

Функция `calculate_risk()` использует правила. Начальная оценка — **0.1**; к ней добавляются:

- **0.3**, если просрочка превышает 30 дней;
- **0.3**, если есть предыдущие дефолты;
- **0.2**, если задолженность превышает 5 000 000;
- **0.1**, если осадков меньше 100 мм.

Итоговая оценка ограничивается значением 1 и округляется до двух знаков после запятой. Это балл по правилам расчёта, а не калиброванная вероятность дефолта.

| Категория | Диапазон оценки | Рекомендация |
|---|---|---|
| `low` | Меньше 0.3 | Стандартное рассмотрение |
| `medium` | От 0.3 до значения меньше 0.7 | Требуется дополнительная проверка |
| `high` | От 0.7 до 1 включительно | Высокий риск. Требуется ручное рассмотрение |

Все девять входных полей валидируются. В расчёте используются просрочка, предыдущие дефолты, задолженность и осадки. Остальные поля описывают хозяйство в контракте запроса.

Готовые примеры:

| Файл | Оценка | Категория |
|---|---|---|
| [examples/low.json](examples/low.json) | 0.1 | `low` |
| [examples/medium.json](examples/medium.json) | 0.4 | `medium` |
| [examples/high.json](examples/high.json) | 0.9 | `high` |

## Хранение и логирование

Результаты хранятся в файле `agro_scoring.db` рядом с `storage.py`. При запуске приложение создаёт таблицу `predictions`, если её ещё нет, и индексы для поиска по `request_id` и категории риска. Для соединений настроено ожидание блокировки до 5 секунд, база использует WAL.

Каждая строка получает собственный первичный ключ `id` и дату `created_at`. Сохраняются `request_id`, `farm_id`, оценка и категория риска, рекомендация, версия модели и источник расчёта: `single`, `batch`, `queued` или `single+llm`. Исходное тело запроса отдельно не хранится. Один `request_id` может встречаться в нескольких строках; одиночный поиск в таком случае возвращает 409.

Запись фиксируется через `commit()` до успешного ответа `/predict`. Результаты сохраняются после остановки и перезапуска приложения, включая `--reload`. SQL-запросы передают входные значения параметрами. Файл базы и его служебные файлы исключены из Git.

Middleware принимает `X-Request-ID` клиента либо создаёт UUID, сохраняет ID в контексте запроса и возвращает его в заголовке ответа. Этот же ID используется при записи прогноза. Для HTTP-запросов в журнал записываются ID, метод, путь, код ответа и время обработки. Время также возвращается в заголовке `X-Process-Time`. Для завершённого расчёта фиксируются `farm_id`, оценка, категория риска и версия модели.
